# Limitations

This file lists what hawkbell does not see, does not prevent, and has not been tested on, because a detection tool that overstates its reach is worse than none. Items come from the red-team review recorded in [ASSUMPTIONS.md](ASSUMPTIONS.md) and from the run records of the built release: [deploy/fleet/VERIFIED.md](../deploy/fleet/VERIFIED.md), [deploy/fluent-bit/VERIFIED.md](../deploy/fluent-bit/VERIFIED.md), [deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md), [test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md), [internal/hookcmd/LATENCY.md](../internal/hookcmd/LATENCY.md) and [packaging/README.md](../packaging/README.md).

## What hawkbell is not

- **Not a tamper-proof control.** Hooks, transcripts and vendor OpenTelemetry are all written by the agent, which runs as the developer. Someone who controls the endpoint can run an agent hook-free, transcript-free, renamed and with a scrubbed environment. hawkbell is aimed at careless and unmodified abuse. Its rules match the mechanics of known supply-chain worms and commodity infostealers in a synthetic scenario corpus that this project wrote from incident descriptions (an expected rule fired on 95 of 100 attacks as written, [bench/results/scenarios.md](../bench/results/scenarios.md)); no recorded attack has been replayed. It raises the cost for a targeted evader on their own machine and does not stop them.
- **Not prevention.** Guard mode answers pre-tool hooks with "ask" or "deny", but when the agent's own hook timeout expires the action goes ahead: always on Copilot CLI, Codex and Gemini CLI, and on Claude Code and Cursor unless the hooks were installed with `hawkbell hooks install --guard --fail-closed` (Claude Code's `onFailure: block` needs Claude Code 2.1.295 or later; Cursor's `failClosed` field has not been checked against Cursor's documentation; [internal/hookinstall/doc.go](../internal/hookinstall/doc.go), "Not supported", and `dialect.go`). So stalling the hook converts a block into an allow. On Codex and Gemini CLI an "ask" (including the answer to a guard timeout or a crashed worker) is shown as a warning and the action goes ahead; only a block stops it there ([internal/hookcmd/doc.go](../internal/hookcmd/doc.go), "What ask and block mean per agent"). Guard mode is advisory.
- **Not an EDR.** It has no kernel sensor of its own. Where the organisation runs osquery evented tables, or an EDR, hawkbell provides join keys (host, pid, process start time, ancestor chain) rather than replacing them.
- **Not an LLM judge.** Detection is deterministic. Whether an instruction file is manipulative, or whether the user actually asked for a deletion, needs a judge; findings that would benefit from one are tagged `escalate` and nothing more.

## Not visible from the surfaces hawkbell uses

| Blind spot | Why | What would see it |
|---|---|---|
| Commands assembled at runtime (`eval` of concatenated strings, interpreter one-liners, heredocs built from character codes, payloads fetched and decoded at runtime) | a static parse of the command line cannot recover text that only exists when the shell runs | syscall and network observation (osquery evented tables, eBPF, Endpoint Security, ETW). hawkbell flags the construct itself as opaque. |
| A script written in one session and executed in another | write-then-run is correlated within a session only | file integrity monitoring |
| Effects of code the agent wrote (what `python build.py` opened or connected to) | hooks report intent, not effect | exec, file and socket events from a kernel sensor |
| Exfiltration from inside a process with no child process | nothing is spawned | network monitoring |
| MCP-over-stdio payloads and model traffic | hooks carry tool names and arguments, not the protocol stream | an MCP or LLM gateway |
| Tool descriptions of MCP servers (tool poisoning, rug pulls of the tool list) | hawkbell never starts an MCP server or runs a discovered binary; it hashes the declaration, not the live tool list | a proxy, or a scanner that executes servers (with the risks that brings) |
| Short-lived child processes when no exec feed is available | polling sees only what is alive at a poll: in the design review a 1 s poll saw 7 of 120 short processes; the monitor polls every 200 ms while an agent runs and every 2 s otherwise (`internal/procmon/procmon.go`) | the Linux process connector (used when permitted; its live test attributed 100 of 100 short children, `TestLiveProcessConnector` in `internal/procmon`) or osquery evented tables (used when the organisation has them on) |
| Agents running in vendor clouds (Claude Code cloud sessions, Codex cloud, Cursor background agents, Copilot coding agent) | they do not run on your endpoints | the vendor's own audit and compliance APIs |
| Agents inside microVM or user-space-kernel sandboxes (Docker Sandboxes, Apple `container`, gVisor, Kata, Firecracker), and inside WSL2 or Docker Desktop / Colima / OrbStack VMs on macOS and Windows | the host cannot see into the guest | an in-guest install |
| Remote development (SSH, Codespaces, devcontainers on another host) | the laptop runs an IDE, the agent runs elsewhere | an install where the agent runs |
| Which account an agent is signed in with (corporate, personal, raw API key) | hooks and transcripts do not report it; vendor OpenTelemetry does | enabling the agent's own telemetry |
| A managed hook that the agent silently ignores | Claude Code uses only the highest-ranked managed source by default, so a file drop is ignored when an MDM profile, a registry policy or a server-managed policy exists; server-managed policy cannot be seen from disk | hawkbell reports hooks as effective only after a real hook event arrives, and reports `shadowed` when it can see a higher-ranked source |

## Integrity limits

- Records produced by hooks are marked `integrity: user`. A process running as the developer can append arbitrary activity claims about its own sessions. It cannot inject findings, health or inventory, and it cannot attribute activity to another user, because the root daemon takes identity from file ownership and re-runs detection itself.
- Forged activity still counts for that account. It can raise findings, change the account's session rows, and keep the account's agents out of the `blind` coverage state, unless the process monitor saw the agent start hook-free (`internal/engine/coverage.go`). The shipped Fleet policies over `hawkbell_detections`, `hawkbell_sessions` and `hawkbell_coverage` do not filter on integrity ([deploy/fleet/lib/stock/policies.yml](../deploy/fleet/lib/stock/policies.yml)). The `integrity` column of `hawkbell_detections` says which rows rest on user-written records.
- In daemonless mode (containers, CI, evaluation) there is no root component: every record is user-integrity and nothing a Fleet policy depends on should be derived from it.
- A tenant HMAC key lives on every endpoint. Keyed digests protect against readers of the log store and against cross-tenant linkage, not against root on the endpoint.
- Sequence numbers and heartbeats detect loss between the sensor and the destination. They do not prove that a record's content is true.

## Delivery limits

- At-least-once delivery holds only with the shipped Fluent Bit configuration (filesystem buffering, unlimited retries). With Fluent Bit defaults, records read but not yet delivered are lost on restart. `hawkbell doctor` checks Fluent Bit's buffering and retry settings when it is given the Fluent Bit API (`output.fluent_bit.api`) or a Fluent Bit configuration file (`--fluent-bit-config`).
- Duplicates are possible. Record ids are deterministic so that destinations can deduplicate.
- A record is capped at 16 KiB after encoding (`output.max_line_bytes`). Larger fields are cut and listed in `truncated`.
- If the local hard cap forces dropping records the shipper has not read, a health record says how many.

## Hook latency

- Every hooked agent event starts the hawkbell binary twice: a supervisor and the worker it supervises. With a release build on the build VM (Linux 6.18, 4 vCPU, load average 1.3 to 1.9), observe mode took 10.42 ms p50 direct, 10.97 ms through `sh -c` and 18.74 ms through `bash -lc`, against 1.33, 2.19 and 9.61 ms for an empty hook (`/bin/true`). That is about 9 ms per event over an empty hook on every launch path (9.1, 8.8 and 9.1 ms), from [internal/hookcmd/LATENCY.md](../internal/hookcmd/LATENCY.md), "Current figures".
- The design target was observe mode "within a few ms" of the empty hook. It is not met. The fix LATENCY.md describes, a small launcher binary that runs only the supervisor (estimated saving 2.5 to 3 ms per call), has not been built: `cmd/` holds only `cmd/hawkbell`.
- Guard mode adds about 6 ms (16.64 ms p50 direct) and in-hook detection about 3 ms more (19.73 ms p50 direct), same source.
- Inside Claude Code 2.1.322, on a loaded host and with an earlier build, the hook cost 12 to 15 ms per event over a drain-only control hook in observe mode ([test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md), section 7).
- Not measured: macOS, Windows (including Defender's cost per process start), a cold page cache after install, and spools on network file systems.

## Platforms

### Linux

Everything in this release was built and run on Linux x86-64. [internal/hookcmd/LATENCY.md](../internal/hookcmd/LATENCY.md) names the machine as a Linux 6.18 Firecracker guest with 4 vCPU and [deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md) as Linux 6.18 in a Firecracker VM; the Fluent Bit and real-agent records say only Linux x86-64, and the Fleet record names its osquery host as Ubuntu. Three gaps remain on Linux itself:

- **The shipped systemd unit has never been started.** The deb and rpm packages were installed, upgraded and removed in Debian bookworm and Rocky Linux 9 containers that have no systemd, so the maintainer scripts' systemd branches did not run ([packaging/README.md](../packaging/README.md)). The Fleet install scripts ran with a fake `systemctl` ([deploy/fleet/VERIFIED.md](../deploy/fleet/VERIFIED.md), "Not verified here"). In every run record the daemon was started by hand or by a test, for example with `nsenter` in [test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md). The unit, [packaging/systemd/hawkbell.service](../packaging/systemd/hawkbell.service), was checked statically only: `systemd-analyze verify` (systemd 255) reports nothing once `ExecStart` names an existing binary ([packaging/README.md](../packaging/README.md)), and `TestScriptsMatchServiceDefinitions` ([packaging/packaging_test.go](../packaging/packaging_test.go)) checks its `ExecStart`, `Group=`, `StateDirectory=` and `StateDirectoryMode=` against the package scripts. So none of the unit's hardening has run with the daemon under it: `ProtectSystem=strict`, `ProtectHome=read-only`, `SystemCallFilter=@system-service`, `RestrictAddressFamilies`, `MemoryDenyWriteExecute`, `MemoryMax=512M`, the capability bounding set, and the `Group=hawkbell` / `StateDirectory=` ownership described in the unit's comments.
- **arm64** was cross-compiled (goreleaser snapshot, before the rename: [packaging/README.md](../packaging/README.md)) but not run.
- The process connector cannot deliver inside a PID namespace, so the real-agent run polled processes instead ([test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md), "Observed, not fixed").

### macOS and Windows

For macOS and Windows the code cross-compiles and the unit tests compile: `GOOS=windows` and `GOOS=darwin` (amd64) `go build ./cmd/hawkbell` and `go vet ./...` passed on 2026-11-12, and `go vet` type-checks the test files as well. The unit tests themselves run on Linux only, so the platform-specific code (Windows ACLs and service control, macOS host identity, the Windows caller-chain snapshot) has been compiled but never executed. No run record contains a run on either system: the Fleet record lists the darwin and windows ATC blocks, the macOS and Windows event tables, the PowerShell scripts and the macOS branch of the shell scripts as not run (no such hosts), and the packaging README marks the launchd plist, the Windows service script, the WiX sketch and the macOS package script as not run. The CI workflow has macOS and Windows jobs but has not run on GitHub yet ([.github/workflows/ci.yml](../.github/workflows/ci.yml)). **No behaviour has been verified on macOS or Windows hardware.** The following must be tested there before any parity claim, and are not claimed today:

Windows
1. Hook latency per agent and launch path (Claude exec form, Git Bash, PowerShell; Codex `pwsh -NoProfile -Command`; Gemini and Copilot PowerShell) with Defender real-time protection on, signed and unsigned.
2. The generated hook command for a path with spaces in each shell, with and without Git for Windows; what Claude Code does on Windows when a hook fails or cannot start (hawkbell registers Claude Code hooks in the exec form, with no shell, on every OS: `claudeHandler` in [internal/hookinstall/dialect.go](../internal/hookinstall/dialect.go); not checked on Windows).
3. Directory ACLs under `%ProgramData%`, including a standard user pre-creating the directory before install.
4. A LocalSystem service reading user profiles: logged-off users, redirected or roaming AppData, FSLogix containers, OneDrive placeholders.
5. Reading another process's environment (native x64, arm64, emulation, sandbox children) and how EDR products react to it.
6. That no file handle held by hawkbell blocks an agent's rename or compaction of its own files.
7. The SMBIOS-derived host id against osquery's `system_info.uuid` on physical and virtual machines.
8. WDAC, AppLocker and Smart App Control with an unsigned binary.
9. WSL2: agents inside WSL are not covered by a Windows install.
10. PowerShell and cmd.exe command analysis. `internal/shellx` parses both with its own tokenizers (`powershell.go`, `cmdexe.go`; the package comment gives the reason: PowerShell has no stable grammar library in Go), and the tests feed it command text only: no test runs PowerShell or cmd.exe, on Windows or anywhere else. Whether the analysis agrees with what those shells do with quoting, escapes, `-EncodedCommand` and variable expansion has not been checked against the shells. The scenario benchmark's mutation operators are POSIX rewrites and count as not applicable to PowerShell and Windows commands ([bench/results/scenarios-notes.md](../bench/results/scenarios-notes.md)).

macOS
1. A root LaunchDaemon without Full Disk Access reading `~/.claude`, `~/.codex`, `~/Library/Application Support/{Cursor,Code,Claude}`, project files under `~/Documents` and `~/Desktop`, iCloud Drive and app containers.
2. A Privacy Preferences Policy Control profile for Full Disk Access against an unsigned or ad hoc signed binary (there is no stable code identity without a Developer ID).
3. Process environment visibility for agent binaries that are code-signing restricted.
4. launchd behaviour, fast user switching and multi-user attribution.
5. Hook behaviour of each agent's real binary, including managed preference domains versus files.

### Agents

One real agent binary has run through the whole pipeline: Claude Code 2.1.322 on Linux, with a local stand-in for the model API ([test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md)). The Codex, Gemini CLI, Copilot CLI and Cursor dialects are built from vendor documentation and source and have not run against the real agents. Unverified agent facts (vendor documentation was unreachable from the build environment, or only one release was tested): all Cursor hook payload details; whether Codex hooks fire identically under `codex exec` and the IDE extension; which Codex release first accepts the JSON block reply hawkbell sends ([internal/hookcmd/doc.go](../internal/hookcmd/doc.go)); Claude Code managed hooks under `--bare` on releases other than the one tested.

## Kubernetes and containers

- The node sensor (the DaemonSet) has been run only under Docker 29.9.2 with runc, overlayfs and cgroup v1 (cgroupfs driver) on one Linux 6.18 VM, with the pod spec reproduced as `docker run` flags. It has not run under a kubelet, containerd's CRI or CRI-O ([deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md)). Container attribution reads `/proc/<pid>/cgroup`. The cgroup v2 layouts (systemd and cgroupfs drivers, kubepods slices for containerd and CRI-O, Podman, the `/..` prefix seen from a private cgroup namespace) are covered only by parser unit tests on sample lines (`internal/platform/container_test.go`, `internal/procmon/parse_test.go`). Not tested on a host: cgroup v2, private cgroup namespaces (containerd's default for non-privileged pods on cgroup v2), AppArmor, SELinux and user-namespaced pods.
- The node sensor needs `hostPID` and the capabilities `SYS_PTRACE` and `DAC_READ_SEARCH`; those are outside the Baseline Pod Security Standard and need an exception.
- **In node mode the sensor sees processes, not hooks or transcripts.** It reports agent roots, their children, the agents' session ids and marker variables, and container ids. The transcript and scan collectors read the sensor container's own file system, so the shipped ConfigMap switches them off ([deploy/kubernetes/configmap.yaml](../deploy/kubernetes/configmap.yaml)). Hooks that run inside another container write to that container's spool, which the node sensor does not read. To get hook events and transcripts from agents in containers, use in-image hook mode, which runs a daemon inside the image (run only under Docker, twice, the same test before and after the rename: a `curl ... | sh` tool call gave an HB-EXEC-001 finding, SPR-EXEC-001 before the rename, on the container's stdout, [deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md)). A confined inventory scan of one container can be run by hand (`hawkbell scan --host-root /proc/<pid>/root`, [deploy/kubernetes/README.md](../deploy/kubernetes/README.md)).
- Without the host network namespace the process connector does not deliver, so the node sensor polls `/proc` (heartbeat surface `processes: degraded/exec_source_poll`, recorded in deploy/kubernetes/VERIFIED.md): processes shorter than the poll interval can be missed.
- Not supported: Fargate and Autopilot-style platforms without host namespaces, Windows containers, sandboxed runtimes (see above), homes on NFS or EFS with root squashing (not tested), processes shorter than the poll interval on the node surface.
- Hooks inside images the platform team does not build are not installable by the node sensor; in-image hooks are telemetry, not a control (their records are `integrity: user`).
- CI support (`hawkbell ci exec`) is experimental and Unix only. It does not cover agents that run inside a `uses:` action step, or Codex (which runs user-level hooks only after the user trusts them); Cursor is covered only with `--in-place` (`hawkbell ci exec --help`).

## Detection quality

- Rule quality is measured by replaying rules over real agent sessions and a scenario corpus; the numbers and their limits are in `bench/results/`. On the release replay, 13 of the 17 alerts in 13,864 tool calls were false (0.94 per 1,000, Wilson 95% [0.55, 1.60]) ([bench/results/release-benign-replay-notes.md](../bench/results/release-benign-replay-notes.md)). The scenario corpus is synthetic and was written by the same project as the rules, so its recall (95 of 100 attacks plain, 94 of 100 under mutations, [bench/results/scenarios.md](../bench/results/scenarios.md)) is an upper bound. The real-session corpus is one workload (Claude Code agents building and red-teaming this project on one Linux machine, as root, in a sandbox; [bench/results/release-benign-replay.md](../bench/results/release-benign-replay.md)), so intervals are wide and the results do not transfer to a fleet without re-measuring there.
- Alert-class rules are tuned on that corpus. That is evidence about their false-positive rate on one workload, not proof of a low rate elsewhere.
- Public rules evaluated on the endpoint can be read and avoided. Re-evaluating shipped events centrally with `hawkbell detect` and rules you do not publish is supported for that reason.
- **Central detection sees only what the privacy profile ships.** `hawkbell detect` evaluates activity and inventory records and skips detections (including `detection.context`), health, posture and summaries (`cmd/hawkbell/input.go`, `accept`). Over the example outbox of the default `minimal` profile ([docs/schema/examples/minimal.ndjson](schema/examples/minimal.ndjson)), it evaluated 2 of the 28 lines, both `inventory.asset` records, and raised none of the 3 findings the endpoint raised for that session. Over the `standard` example ([standard.ndjson](schema/examples/standard.ndjson)) it evaluated 11 of 37 lines (9 activity, 2 inventory) and raised the same 3 findings (HB-CRED-002, HB-EXEC-001, HB-EXFIL-005). Both runs: `hawkbell detect --no-host-rules --fail-on none --json`, 138 rules, rules hash `82523dea0cec`, 2026-11-12. In `standard`, central rules see redacted fields only: no prompt text, and tool input and output only as input key names, sizes rounded up to a power of four and keyed digests ([EVENTS.md](EVENTS.md#what-each-profile-ships)). In no profile, `full` included, does `hawkbell detect` see content written by file tools, tool output or MCP call arguments: those are read only from the local content of hook spool records (`cmd/hawkbell/input.go`, `spool`), which hawkbell never ships, so the rules over them and write-then-run correlation run on the endpoint only ([DESIGN.md](DESIGN.md#trust-boundaries), item 9).
- There is no behavioural baseline beyond first-seen egress hosts and MCP servers.
- Paths are put in one canonical form lexically (`.` and `..`, doubled separators, `/proc/<id>/root` for any id, a `cd` on the same command line, a one-character bracket glob such as `[s]`, Windows prefixes, local admin shares and trailing dots); nothing is resolved on disk: no file is opened and no link is followed (`internal/pathcanon/pathcanon.go`). Shell paths stay relative to the session's working directory in `shell.reads`, `shell.writes`, `shell.deletes` and `shell.changes`; the `*_classes` features classify them joined with it, so rules that match a path class see them, and HB-EVADE-002 matches the `sensor_self` class beside its anchored path list. Rules that anchor a regex on those lists (HB-DESTR-006 for system directories, HB-DESTR-008 for personal folders) still need the location spelled out, so `rm -rf lib` with the session in `/usr` does not raise HB-DESTR-006. Joining them with the session directory would make every delete inside a workspace under `/opt`, `/srv` or `~/Documents` match.
- Globs are matched only through path classes, which ask whether a glob could name a file of the class. A glob over a location no class covers, and a glob whose literal text is too short to tell (`/usr/local/bin/*` is not the sensor's binary for `sensor_self`), are not resolved. File tools do not expand globs: a Write to `/etc/[h]awkbell/disabled` creates a file under a directory literally named `[h]awkbell`, so it is not the sensor's kill switch.
- These still name a file under a second spelling: a symlink, hard link, junction or bind mount made by an earlier tool call; a `cd` in an earlier tool call; a directory the analysis cannot resolve (`cd "$X"`, `cd -`, a `popd` past the start of the stack, `~x` in a shell list, though classes resolve `~x` to `/home/x`), after which relative operands are recorded as written (`internal/shellx/sem_cwd.go`); `..` directly after a variable the analysis cannot resolve (`$X/../etc` keeps `$X/..`); case variants on Linux; Windows 8.3 short names other than `GIT~1`, and per-drive working directories on Windows (`internal/classify/doc.go`). A link or bind mount made on the same command line is followed: an operand through it is recorded both as written and as the path it reaches. A link or bind mount that reaches the sensor's configuration, state, spool, socket or service files raises HB-EVADE-002 when it is made, which covers a write through it in a later tool call; one to the sensor's binary or logs does not, and for other files a link made by an earlier tool call is not followed.
- A file in the session's own temporary directory (a temporary path with a component equal to the session id, such as Claude Code's scratchpad) is not counted as third-party content when it is read, except under a dependency tree or a download directory inside it. Content the agent downloaded there sets `untrusted_input` when it is downloaded, not each time it is read again.

## Operations

- Binaries are unsigned in this release. The build flags aim at reproducible output (`-trimpath`, no build id, CGO off) and goreleaser writes checksums; two builds of one version on one machine and toolchain gave the same SHA-256, which is not a check across machines ([packaging/README.md](../packaging/README.md)). Notarized macOS packages and Authenticode-signed MSIs need a maintainer signing identity; signing (cosign) and SBOMs (syft) were skipped in the one goreleaser snapshot run.
- Per Fleet's documentation for 4.94, not tested ([deploy/fleet/README.md](../deploy/fleet/README.md#fleet-free-and-fleet-premium)): hosts enrolled with plain osquery cannot run scripts on any tier, and software deployment and the `install_software` / `run_script` policy automations need Fleet Premium. The design review saw Fleet answer `422 Scripts are disabled for this host` on a plain osquery host ([ASSUMPTIONS.md](ASSUMPTIONS.md)). The same README section says which install path needs which tier.
- On hosts without SMBIOS data, osquery invents its own host UUID; an exact join between hawkbell's stream and Fleet hosts then requires the extension (which asks osquery) or explicit configuration.
- The product catalog goes stale quickly: agents release often and rename packages. The research for this project counted about 158 stable releases of four major agents in 90 days; that count is not reproduced in this repository. The embedded catalog's fingerprints were checked on 2026-11-11 (header of `internal/catalog/data/agents.yaml`), and fields that could not be checked are listed per product under `unverified`. `hawkbell catalog verify` asks the npm and PyPI registries about the catalog's package names; treat anything not verified in the last 30 days as unverified.
