# Assumptions ledger: how the design was attacked before it was built

Before any product code existed, the first design ("v0") was written down as 37 explicit, numbered assumptions and handed to nine hostile reviewers, review sessions of this build each given a different persona (the lenses below). Every reviewer had to break assumptions with evidence: a cited primary source or, preferably, an experiment run against real software (Fleet 4.94.1 with an enrolled osquery 5.19 host, the Fluent Bit 5.2.0 image, Go prototypes). A second, independent reviewer then tried to refute each finding. The first design is [design/v0.md](../design/v0.md) (assumptions in sections 11 and 12). Each reviewer's notes are in [redteam/](../redteam/), linked in the table below, and the lead's ledger of verdicts and decisions is [design/DECISIONS.md](../design/DECISIONS.md). They are historical records written on 2026-11-11; the scripts and outputs they name are on the build machine, not in this repository. This file records what was assumed, what broke, the evidence, and what changed. It is kept in the repository because the failures are more useful to a prospective user than the features.

Verdicts: **broken** (the claim was false or the design as written failed), **weakened** (true only with a stated restriction), **holds** (a serious attempt to break it failed).

Scope of the evidence: all experiments ran on one Linux x86-64 sandbox VM on 2026-11-11, mostly against prototypes rather than the built release. Nothing here is a measurement on Windows or macOS hardware; see [LIMITATIONS.md](LIMITATIONS.md) for the hardware test matrix that follows from that. The "Changes" paragraphs below say what was built in response; where this file was checked against the built code and the release's run records (2026-11-12: [deploy/fleet/VERIFIED.md](../deploy/fleet/VERIFIED.md), [deploy/fluent-bit/VERIFIED.md](../deploy/fluent-bit/VERIFIED.md), [deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md), [test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md), [internal/hookcmd/LATENCY.md](../internal/hookcmd/LATENCY.md)), the paragraph says what the release does and where that is recorded.

## What broke, with the evidence

### Transport: "NDJSON files plus Fluent Bit tail is at-least-once" (A14) — broken
- With Fluent Bit's default memory buffering, the tail input commits its file offset when it reads a line, not when an output delivers it. Test: 5,000 events, output unreachable, Fluent Bit restarted. Delivered after recovery: **0 of 5,000** with memory buffering (graceful stop or default retry), **5,000 of 5,000** with `storage.type: filesystem` and `retry_limit: no_limits` even after SIGKILL.
- Pruning segments by deletion while Fluent Bit lags lost data silently: **3,552 of 40,000** delivered. With inode reuse and default tail settings the first 1,000 of 3,000 records of the next segment were skipped; `db.compare_filename: true` fixed it.
- One 200 KB event line stopped the whole segment with default tail settings (32k buffer); with `skip_long_lines` the event vanished.
- Concurrent appenders did hold: 0 torn lines in 29,568 lines up to 1 MB from six processes using one `write(2)` per line on `O_APPEND`.

Changes: the shipped Fluent Bit configuration is part of the contract (filesystem buffering, unlimited retries, filename comparison, long-line skipping); every emitted line is capped at 16 KiB with truncation recorded; the sensor reads Fluent Bit's tail database and prunes only segments that were read, and emits a health error with counts when the byte cap forces dropping data a configured consumer has not read (with no consumer configured it cannot tell, and only heartbeat counters show what the cap removed; [LIMITATIONS.md](LIMITATIONS.md#delivery-limits)); `doctor` flags an unsafe shipper configuration when it is given the Fluent Bit API or configuration file. The kill test is an end-to-end test against the real image (`test/e2e`, `HAWKBELL_E2E_FLUENTBIT=1`); on Fluent Bit 5.2.0 with the shipped configuration it delivered 5,000 of 5,000 records after SIGKILL ([deploy/fluent-bit/VERIFIED.md](../deploy/fluent-bit/VERIFIED.md)). It is part of the `e2e-linux` job in `hawkbell/.github/workflows/ci.yml`, which pulls `fluent/fluent-bit:latest` rather than a pinned 5.2.0. GitHub does not run that file from its location under `hawkbell/`, and it has never run ([.github/workflows/ci.yml](../.github/workflows/ci.yml), header). The claim is now "at-least-once only with filesystem buffering".

### Integrity: "a user-writable spool is an acceptable trade-off" (A28) — broken
- Forgery, not deletion, is the real risk. Three lines were appended to a spool file as the user: one genuine, one forged detection marked "cleared, approved by security", one forged activity record attributed to a different user. Fluent Bit shipped all three verbatim.
- A root Fluent Bit tailing a user-owned directory shipped whatever file the user symlinked into it (confused deputy).

Changes: hooks write only to a per-user spool that nothing ships directly in the supported fleet mode. The root daemon ingests spools with no-follow, non-blocking opens and an owner check on the open descriptor, accepts **only activity claims** from them (a spool can never inject detections, health, inventory or posture), sets user and host from the file owner rather than the payload, stamps `integrity: user`, and re-runs detection itself. Fluent Bit tails only the root-owned outbox. Every record carries `integrity`. The aim was that Fleet policies depend only on root-integrity data; as built, no spool line can itself be a detection, health, inventory or posture record (a line of another kind is refused, and the detection, health, asset, check and summary fields of an activity line are cleared: `decode` in `internal/spool/reader.go`), but the shipped policies over `hawkbell_detections`, `hawkbell_sessions` and `hawkbell_coverage` do not filter on integrity, so activity a user forges for their own account can raise detections, change session rows and keep an agent out of the `blind` coverage state ([deploy/fleet/lib/stock/policies.yml](../deploy/fleet/lib/stock/policies.yml), `internal/engine/coverage.go`; see [LIMITATIONS.md](LIMITATIONS.md#integrity-limits)). Daemonless operation still exists for containers, CI and evaluation and is labelled as such.

### Corroboration: "three independent surfaces" (thesis, A5, A6) — broken
- Hooks and transcripts are both written by the agent. The third surface, process polling, saw **7 of 120** short-lived child processes at a 1 s interval and none of the 100 shortest at 250 ms.
- osquery's audit-backed `process_events` captured **5 of 5** millisecond-lived processes with full command lines, and they reached the local results log within one 5 s interval. Its BPF publisher failed in the same VM while reporting `active=1`.
- Disagreement between surfaces can be driven to zero (hook-free plus transcript-free plus relocated config) or forged upward (write a transcript for tool calls that never ran).

Changes: the design now speaks of two agent-reported surfaces (hooks, transcripts; vendor OpenTelemetry is a third of the same kind) plus one OS surface whose fidelity is reported in health. The poller is described as what it is (agent presence, flags, long-lived children such as MCP servers and tunnels). Exec ground truth comes from the Linux process connector where available, then from osquery evented tables pulled over osquery's own extension socket. The verifier rejected the first fix (a Fleet-scheduled `process_events` report): it would send every command line on the host to the Fleet server unredacted, and plain osquery enrolled in Fleet has no local results file to tail. Because a provider can report itself active while delivering nothing, the monitor execs a canary periodically and reports whether the exec feed saw it. A "hook bypass suspected" finding (HB-COV-901) requires a root-observed surface; with only self-reported surfaces it is a low-severity signal (HB-COV-902), at most one per session, that is never attributed across users (`internal/engine/coverage.go`). As built, the process connector delivered in a live test as root (`TestLiveProcessConnector` in `internal/procmon`: 100 of 100 short children attributed), but not in the recorded end-to-end runs: inside a PID namespace (the real-agent run) and in a pod without the host network (the node sensor) the monitor polled ([test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md), [deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md)).

### Hosting the daemon inside the osquery extension (A17) — broken
The extension process exited 3 s after osqueryd was killed, taking any hosted collector with it. The extension is tables only.

### Host identity equals osquery's `system_info.uuid` (A20) — broken
On a machine without SMBIOS data, four osquery databases produced four different random UUIDs, none related to `/etc/machine-id`; on hardware with DMI the Linux source is readable by root only. Changes: identity order is explicit configuration, then a file written by the extension (which asks osquery itself), then hardware identifiers, then machine-id; the source is reported in health. An exact join with Fleet requires the extension or explicit configuration.

### Fleet tables through ATC (A16) — weakened
- WAL mode: 0 torn reads of 75 while a writer committed every 50 ms. Rollback-journal mode: torn snapshots with no error (4 of 10 through Fleet).
- A missing database reads as zero rows with no warning, so every "no critical findings" style policy **passes** when the sensor is absent.
- No predicate pushdown: 10,000 rows cost 26 ms and 12 MB per query, 100,000 rows 270 ms and 107 MB, and one live query over 300,000 rows tripped the 200 MB watchdog while Fleet reported success.
- Replacing the database by rename replayed a stale WAL over the new file.

Changes: WAL only and never rename; row caps per table; every policy also requires a fresh heartbeat row so absence fails closed; the extension is the recommended path at scale; ATC remains the ten-minute start.

### Privacy: "metadata tier by default" (A26) — broken, critical
The proposed default shipped user name, working directory, file paths, command lines and web search queries for every tool call: identified behavioural monitoring. An unkeyed SHA-256 of prompts was reversed for 4 of 6 short sample prompts with a 1,600-entry dictionary built in 1 ms.

Changes: three emit profiles. `minimal` is the default: findings, inventory, posture, health and per-session summaries leave the host, activity stays in a local ring and travels only as context attached to a finding. `standard` ships activity with field-level redaction. `full` adds redacted content. Digests of content are HMAC with a tenant key or are not emitted. Exclusions by path, repository and user apply before any content is processed. `privacy show`, `privacy tail` and `privacy purge` exist for the people being monitored. Retention has stated defaults ([PRIVACY.md](PRIVACY.md)).

### Redaction by patterns and entropy (A29) — broken
8 of 17 invented secrets survived (hex tokens at the entropy threshold, values after unlisted flags); over-redaction removed hosts and an image digest. Changes: redaction is structural first (the parsed command says which argument is a credential for `mysql -p`, `curl -u`, `-H Authorization`, assignments to sensitive names, URL userinfo), patterns second; a canary corpus is pushed through every profile by the unit tests, which fail on any leak and measure over-redaction (`internal/privacy/canary_test.go`; on 2026-11-12: 179 canaries, 9,144 records, 0 leaks; 0 of 52 benign values lost). The plan to publish the rates with each release in `bench/results/` was not carried out: the counts appear only in `go test -v` output, and the CI workflow that would run the tests has not run on GitHub yet.

### The sensor as attack surface (A27) — broken in several places
- A root reader followed a user-placed symlink; a FIFO named like a config blocked the reader indefinitely.
- Rule cost scales with input: 10 patterns over 1 MiB took 290 ms; compiling 300 regexes costs 77 ms per process.
- An unrecovered Go panic or runtime fatal error exits with status 2, and exit 2 means "block" in every agent's hook contract: a crashing observe-only hook would block tool calls.

Changes: no path taken from hook input is ever opened; all reads of user-controlled trees use no-follow, non-blocking opens and check type and owner on the descriptor; content scans are bounded to head and tail windows with a wall-clock deadline; a crash or timeout in the hook can never block the agent: the second reviewer showed that an in-process recover handler misses 4 of 5 Go crash classes (each exits 2, which agents read as "block"), so the hook runs its work in a supervised worker process. As built (`internal/hookcmd/doc.go`), `hawkbell hook` exits 0 in every case, and no code path uses exit 2. When the worker crashes, hangs, times out or writes a broken reply, the supervisor answers with an empty reply (proceed) in observe mode and with the agent's "ask" in guard mode; on Codex and Gemini CLI that "ask" is a warning and the action proceeds. A guard block is expressed only in the JSON reply, including on Codex, whose deny is sent as the JSON form Codex accepts on exit 0 (checked against Codex's source on 2026-11-12; which Codex release first accepts it is unverified). Not covered: a signal from outside that kills the supervisor itself (the agent's own hook timeout, the OOM killer). Scan and collection packages may not import `os/exec`, enforced by tests (`TestNoExecInScanPath` in `internal/discovery`, `TestNoExecImport` in `internal/procmon`).

### Shell analysis as a robust basis for rules (A9) — broken against a motivated evader
A canonicalizer built on a real POSIX parser saw `curl ... | sh` but not `eval` of runtime-assembled strings, interpreter one-liners, heredocs built from character codes, decoded payloads fetched at runtime, or a script written by an earlier tool call and then executed. Changes: these constructs are surfaced as an explicit `opaque` feature (`shell.opaque`) that rules score, write-then-run is correlated across the events of one session, and the documentation lists what cannot be seen without a kernel sensor ([LIMITATIONS.md](LIMITATIONS.md)).

### Co-occurrence "lethal trifecta" as an alert (A10) — broken
Replayed over 37 real agent transcripts with no attacker present (the subagent transcripts of one build session of this project, one user, 53 minutes): `untrusted_input` was set in 68% of transcripts and `egress` in 65%, so the rule reduced to "a secret-class path was touched". Counted per transcript it fired once, but the second reviewer showed that this rate does not carry over to sessions: keyed by session id, as the rule was designed, it fired 13 times in under an hour of ordinary work, and the single per-transcript hit depended on counting key creation as a secret read and a first-party MCP listing as untrusted input. Either way the positive predictive value at fleet scale is near zero. Regex-on-text rules produced dozens of false hits that parsed-fact rules did not, and flat predicates over arrays over-matched 3.3x to 3.6x because they cannot say "the same command".

Changes: rules have three classes (signal, finding, alert); co-occurrence is a signal (HB-SEQ-001); the alert-class rule for this pattern (HB-EXFIL-001) requires data flow (a secret value the agent actually read later appears, raw or encoded, in an outbound command, URL or tool input); shell rules may match parsed facts only, enforced by lint (`raw_command_match` in `internal/rules/lint.go`); a bound quantifier (`any_command`) expresses "the same command"; first-seen baselines and operator suppressions are first-class; rule quality is measured by replay over real sessions, not asserted from inline tests. The release has 138 rules: 14 alert, 88 finding and 36 signal (`hawkbell rules list`). On the release replay (136 agent threads, 13,864 tool calls) 13 of the 17 alerts were false, 0.94 per 1,000 tool calls, Wilson 95% [0.55, 1.60] ([bench/results/release-benign-replay-notes.md](../bench/results/release-benign-replay-notes.md)).

### Guard mode as prevention (A12) — unsafe as a control
Hook timeouts fail open, so stalling the hook converts "block" into "allow"; as built, only Claude Code and Cursor hooks can be installed fail-closed (`hawkbell hooks install --guard --fail-closed`; Cursor's field is unverified), and Copilot CLI, Codex and Gemini CLI always fail open on a timeout (`internal/hookinstall/doc.go`). Guard mode is opt-in, labelled advisory, answers "ask" on deadline (default 150 ms), and is never described as prevention. On Codex and Gemini CLI an "ask" is a non-blocking warning; only a rule with response `block` under `guard.max_response: block` stops the action there (`internal/hookcmd/doc.go`).

### Managed hooks behave as documented everywhere (A1, A24) — broken in specifics
- Claude Code ignores a file-dropped managed hook when a higher-precedence managed source exists (MDM plist, HKLM value or server-managed policy; the default is first-wins).
- One hook command string cannot be valid in Git Bash, PowerShell, cmd and sh; Codex launches hooks through the user's login shell.
- POSIX permission bits do nothing on Windows; WSL2 agents are invisible to a Windows binary; a Go binary has no stable code identity on macOS without a signing identity.

Changes: the installer uses exec-form hooks where the agent supports them and per-shell strings elsewhere; `hooks status` reports `shadowed` and insecure permissions; coverage is driven by a per-session "hook loaded" signal rather than file presence; platform claims are limited to what was tested.

### Kubernetes: "hostPID DaemonSet sees agents in containers" (A25) — broken as stated
`hostPID` alone cannot read non-root agents' files or environment (it needs `SYS_PTRACE` and `DAC_READ_SEARCH`); reading through `/proc/<pid>/root` followed tenant-planted symlinks to host files; microVM sandboxes are opaque. Changes: a read-only node sensor with exactly those two capabilities for runc-class runtimes, opens confined with `openat2(RESOLVE_IN_ROOT)`, events on stdout, plus in-image hook mode; an explicit unsupported list. As built and run ([deploy/kubernetes/VERIFIED.md](../deploy/kubernetes/VERIFIED.md)): under Docker with runc and cgroup v1 only, no kubelet; the node sensor attributes processes in other containers but its daemon does not read their hook spools, transcripts or configuration (in-image hook mode collects hooks; a one-off `hawkbell scan --host-root /proc/<pid>/root` reads configuration); a seccomp profile was added after a review showed that `CAP_SYS_PTRACE` with `hostPID` let a compromised sensor attach to root processes.

### "No server of our own" (A30, A33) — weakened
Fleet answered `422 Scripts are disabled for this host` on the stock-osquery host: there is no Fleet channel that can deliver a rule pack or a suppression there, policies run hourly and webhooks daily. Changes: rules, lists, suppressions and catalog overlays are pulled as an ed25519-signed bundle from an operator-supplied static URL, with no downgrade and the installed version visible in every finding and in the health table; `detect` re-evaluates shipped events centrally; a session summary stream supports fleet-wide questions.

### The thesis itself — broken as first written
The first draft claimed that no open-source tool gives a real-time, vendor-neutral signal. Research found that perplexityai/numbat (hooks for 28 agents, on-endpoint rules, opt-in enforcement) and Agent Beacon (29 runtimes, signed packages) already exist, and that Fleet's own agent ships inventory tables. What survived a deliberate search for an open-source equivalent: none exposes sensor health, per-agent hook coverage and findings as osquery tables with Fleet policies that fail closed, ships a Fluent Bit configuration tested by killing Fluent Bit with its output down, or corroborates the agent's self-reported surfaces with a root-observed one. Pieces exist elsewhere and are credited: Agentmetry reports hooks that are installed but silent and ships a 57-case benchmark with benign cases, agent-bom has Kubernetes content, and EDR vendors correlate agent activity with OS telemetry in their own products. The project is positioned as that assurance and integration layer, and it accepts numbat output as an input.

## Findings the verification pass overturned or corrected

The second reviewer was asked to refute, and did so in several places. These corrections are part of the record. The `--bare` row and the conclusions of the OpenTelemetry and adapter rows were passed to the builders in [design/BUILD-B.md](../design/BUILD-B.md), Addendum 2. The verifiers' own scripts and outputs are on the build machine, not in this repository:

| Finding | Correction |
|---|---|
| "`--bare` removes the hook surface and will become the default for `claude -p`" | Not confirmed. On the Claude Code release tested, managed-tier tool hooks still run under `--bare`; only the managed SessionStart hook and user/project hooks are skipped. `--bare` is recorded as a session attribute, session start is synthesized from the first event of an unseen session, and "hookless" is raised only when tool activity appears on another surface with no hook events. Only one release was tested, so this check belongs in CI per release. |
| "Compare vendor OTel `hook_execution_complete` counts with hook events to prove the hook ran" | Unsound as stated: that event aggregates every matching hook and cannot tell a managed hook from a user hook. OTel is another agent-reported surface on an unauthenticated loopback port; it never satisfies a tamper check alone. |
| "Write the agent's managed OTel settings at install" | Each agent has one OTLP endpoint per signal, so writing it would take over an organisation's existing telemetry. It is opt-in and refused when an endpoint is already pinned. |
| "Capture the agent binary's SHA-256 on every hook event" | Hashing a large agent binary per event costs roughly 80 times the hook budget warm. Hooks record pid, start time, path and the ancestor chain. The planned hash cache keyed by device, inode, size and mtime was not built: the release hashes no agent binary, and an agent asset's `sha256` is a digest of what was observed (version, path, evidence, risk flags), not of the binary (`internal/discovery/emit.go`, `observationDigest`; `internal/discovery/doc.go`, "Not supported"). |
| "Drop the Gemini and Cursor dialects and take those agents through another sensor's output" | Rejected for Cursor (one of the three agents the brief names would then depend on a second binary). An adapter also reads a pre-1.0 schema from files the monitored user owns, so adapter records are stamped user-integrity and schema versions are checked. |
| "Recast the project as only an assurance layer over other sensors" | Too far: it abandons the goal of a detection platform. The headline is an agent detection platform whose telemetry is attested; ingesting other sensors is an addition. |
| "There is no Fleet channel on plain osquery" | Overstated: osquery's config channel reaches stock osquery on Fleet Free within one refresh. What is missing is a desired-state file or script primitive, which the signed bundle provides. |

## Not verified

- Anything on Windows or macOS hardware (hook latency with Defender, ACLs, service behaviour, TCC and Full Disk Access, WSL, code signing). The release cross-compiles for both and its test files type-check there (`go vet`); no run record contains a run on either.
- Whether Claude Code managed hooks load under `--bare` on releases other than the one tested; whether Codex hooks fire identically under `codex exec`; all Cursor hook payload details (the vendor documentation was unreachable from the build environment). One real agent has run through the built pipeline: Claude Code 2.1.322 on Linux, with a stand-in for the model API ([test/e2e/REAL-AGENT.md](../test/e2e/REAL-AGENT.md)).
