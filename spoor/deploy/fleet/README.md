# spoor for Fleet

Fleet content for spoor: labels, policies and reports over spoor's state
database, agent options that expose it to osquery, install scripts, and
package examples. Written for Fleet 4.94 (its vocabulary: *fleets*, not
teams; *reports*, not queries) and osquery 5. What was checked against a
live Fleet 4.94.1 server and osquery 5.19 host, and what was not, is in
[VERIFIED.md](VERIFIED.md).

```
deploy/fleet/
  lib/                      GENERATED by internal/fleetgen (do not edit)
    agent-options.atc.yml     ATC fragment: the spoor_* tables, one block per OS
    agent-options.example.yml the fragment merged into a typical base (tier 2)
    agent-options.base.example.yml  the same base without spoor ATC (tier 3)
    stock/                    profile for plain osquery: labels, policies, reports
    fleetd/                   profile for fleetd hosts (adds Fleet's ai_tools table)
    builtin/                  tier 1: Fleet's ai_tools only, no spoor binary
    opt-in/                   exec-event reports (privacy warning inside)
    CONTENT.md                every label, policy and report with its window
  scripts/                  Fleet scripts: install/uninstall (sh, ps1), post-install
  software/                 *.package.yml examples (Fleet Premium)
  gitops/                   example default.yml (Free) and fleets/ file (Premium)
  verify.sh                 live verification; VERIFIED.md is its captured output
```

Regenerate `lib/` after changing the state tables, the catalog or the
generator: `go test ./internal/fleetgen -run TestGolden -update`. The golden
test fails when the committed files differ from the generator's output.
`spoor export fleet` (cmd/spoor) is meant to write the same files with a
host's own paths through `fleetgen.Generate`.

## Three tiers

| | Tier 1: no binary | Tier 2: scan + ATC | Tier 3: daemon + extension |
|---|---|---|---|
| On the host | fleetd 1.59.0+ only | spoor (scheduled `spoor scan --state`, or `spoor run`) | `spoor run` service + spoor registered as an osquery extension |
| How osquery reads spoor | (nothing to read) | auto table construction from agent options | extension tables: typed columns, constraint pushdown |
| Content | `lib/builtin` | `lib/stock` or `lib/fleetd` + `lib/agent-options.atc.yml` | `lib/stock` or `lib/fleetd`, no ATC |
| What you get | inventory and configuration flags from Fleet's own `ai_tools` table (Fleet's agentic-detector integration) | spoor inventory, posture, hook coverage, sensor health, detections as recorded by whatever writes the state DB | everything in tier 2, plus real-time hooks, transcripts, process monitor and detections from the daemon |
| What it cannot do | no detections, no hook coverage, no history between queries (`ai_tools` is computed when queried), nothing on plain osquery | ATC reads the whole table for every query (all columns TEXT); a scan-only setup sees no agent activity | |

Tiers 2 and 3 are alternatives: ATC and the extension both provide the
`spoor_*` table names. With the ATC agent options in place, osquery 5.19
refuses the extension ("Registry item spoor_agent_processes conflicts with
another item of the same name") and the extension restarts every few
seconds (VERIFIED.md). So the agent options and the install method must be
the same tier, host by host:

- **Tier 3** (the examples in `gitops/`): agent options without spoor's ATC
  tables (`lib/agent-options.base.example.yml` shows a base;
  `fleetgen.StripAgentOptions` removes them from yours), install scripts at
  their default `TIER=extension`, packages with the `register-extension`
  post-install script.
- **Tier 2**: `lib/agent-options.example.yml` (your options with the ATC
  fragment merged in), `TIER=atc` in both install scripts (it skips, and
  unregisters, the extension), and no `post_install_script` in the package
  files.

Fleet runs scripts without environment variables, so the tier is set in the
script file itself, next to the download URLs and hashes (`TIER=` in
`install-spoor.sh`, `$Tier` in `install-spoor.ps1`); `SPOOR_TIER` only
overrides it when you run a script by hand. A test in `internal/fleetgen`
holds every example file to one tier.

**fleetd hosts where Fleet manages osquery extensions.** When Fleet's
`extensions` agent option (Premium, your own TUF server) puts anything in
orbit's own `extensions.load` (`/opt/orbit/extensions.load`,
`C:\Program Files\Orbit\extensions.load`), orbit starts osquery with
`--extensions_autoload` pointing at that file, after the flagfile, and
osquery ignores its default `extensions.load` (orbit/cmd/orbit/orbit.go).
An extension registered there never loads. The extension tier therefore
refuses such hosts: the install scripts and the post-install script exit
with that reason (for a package, Fleet then marks the install failed and
rolls it back). On those hosts publish spoor through the `extensions` agent
option, or use tier 2. If Fleet starts managing an extension on a host
after spoor was registered, spoor's extension stops loading; the **"spoor
tables unavailable"** label lists such hosts.

Pick the profile by agent: `fleetd` for hosts running Fleet's
agent (its policies also read `ai_tools`, which plain osquery does not have),
`stock` for everything else. The `stock` profile also works on fleetd hosts.

## Fleet Free and Fleet Premium

From research/fleet.md and the fleet-operator red team (Fleet documentation,
4.94.1):

| Feature used here | Free | Premium |
|---|---|---|
| Global labels, policies, reports, agent options; GitOps `default.yml` | yes | yes |
| Policy webhooks (`failing_policies_webhook`), log destinations for reports | yes | yes |
| Saved and ad hoc scripts (`controls.scripts`), batch runs | yes, but only on fleetd built with `--enable-scripts` (or macOS MDM); plain osquery cannot run scripts at all | same |
| Fleets (formerly teams): per-fleet agent options, policies, reports | no: one global configuration | yes |
| Software deployment (`software.packages`, `*.package.yml`), self-hosted needs S3 | no | yes |
| Policy automations `install_software` / `run_script` | no | yes |
| Labels on reports, policies, software (`labels_include_any` ...) | no | yes |
| TUF-managed `extensions` agent option | no | yes, plus your own TUF server for all of fleetd |

So on Free: apply the global GitOps entries, run `scripts/install-spoor.sh`
or `.ps1` per host or as a batch run (fleetd with scripts enabled), or
install the deb/rpm/pkg with your existing tooling; on Premium, use
`software/*.package.yml` and the install-on-failure policies in
`gitops/fleets/workstations.yml`. Those policies check the binary only (the
state database survives an uninstall, so it must not count as installed)
and are scoped by two labels the file defines, "Debian-family Linux" and
"Red Hat-family Linux" (from `os_version`: Fleet's built-in "Ubuntu Linux"
misses Debian, "Red Hat Linux" misses Rocky and Alma). Because they
reinstall spoor wherever the binary is missing, move a host out of the
fleet before uninstalling spoor from it.

## Fail-closed policies and the two heartbeat windows

A missing state database reads as zero rows, under ATC and under the
extension alike, so a policy "no critical detection exists" would pass on a
host where the sensor was never installed, has stopped, or had its database
deleted. Every spoor policy therefore also requires a fresh
`spoor_health.heartbeat` (built with `state.PolicySQLWithin`), and two
windows are used:

- **"spoor - sensor is reporting"** accepts a heartbeat up to **30 minutes**
  old. This is the policy to alert on, and the "spoor sensor unhealthy" label
  uses the same window.
- **Every other spoor policy** embeds a **24 hour** guard. A removed sensor
  or a deleted database turns them red within a day, but a laptop that wakes
  after a night's sleep does not turn every policy red at once.

The trade-off, stated plainly: for up to 24 hours after a sensor stops, the
"no X" policies keep reporting the last state the sensor saw, and only the
sensor policy tells you the data is stale. If you act on the "no X"
policies, gate on the sensor policy too. Fleet evaluates policies about
once an hour, so detection and bypass policies look back 24 hours rather
than at "now".

Under the hood a policy is

```sql
SELECT 1 WHERE EXISTS (SELECT 1 FROM spoor_health
                       WHERE heartbeat >= strftime('%Y-%m-%dT%H:%M:%S.000000Z', 'now', '-86400 seconds'))
         AND NOT EXISTS (<the violation>);
```

A host whose spoor tables are not loaded at all (extension not running, ATC
agent options not delivered) cannot run these queries; Fleet shows *no
response*, which counts as neither pass nor fail. The label **"spoor tables
unavailable"** catches those hosts using only osquery's own tables.

## Agent options: merge, never replace

`lib/agent-options.atc.yml` is a **fragment**. Fleet replaces agent options as
a whole: applying the fragment as your agent options drops your existing ATC
tables, decorators and options. Fleet also does not merge
`overrides.platforms.<os>` with `config`: a darwin or windows override must
carry that OS's complete configuration. Linux hosts read `config` (their
`os_version.platform` is the distribution name, so an override keyed `ubuntu`
would hide `config` from them). To merge:

1. add the `config.auto_table_construction` entries to yours (and to every
   override keyed by a Linux distribution);
2. add the darwin and windows entries to your existing overrides for those
   OSes, or, if you have none, create each as a copy of your whole `config`
   first and then add the entries;
3. validate with `fleetctl gitops -f default.yml --dry-run`.

`lib/agent-options.example.yml` shows the result on a typical base, and
`fleetgen.MergeAgentOptions` does the same merge in code (verify.sh uses it).
State database paths default to `/var/lib/spoor/state.db`,
`/Library/Application Support/spoor/state.db` and
`C:\ProgramData\spoor\state.db`. Custom paths must be absolute and clean
(no `//`, `.` or `..` element, no trailing separator, backslashes only on
Windows) and free of `%`, `*`, `?`, `[`, `]`, `{` and `}`: ATC expands
osquery's `%` wildcard and glob patterns (osquery 5.19 read two databases
for `spoor?`, `spoor[AB]` and `spoor{A,B}`) and reports canonical paths,
while the "spoor installed" label compares paths exactly. ATC needs the database in WAL mode, which spoor always uses
(rollback-journal files were read torn by ATC in the red team's tests).

## Install scripts

`scripts/install-spoor.sh` (macOS, Linux) and `scripts/install-spoor.ps1`
(Windows) are Fleet scripts, each under Fleet's 10,000-character limit for
script contents. Edit the URL and SHA-256 of each build and the tier at the
top (a value may be a Fleet custom variable). They:

- download over HTTPS and refuse to install unless the SHA-256 matches;
- create the `spoor` group (outbox readers), the configuration and data
  directories with explicit owners and modes, and the configuration via
  `spoor export config` when none exists;
- install the service (the same systemd unit and launchd plist as
  `packaging/`; a test keeps them identical) and restart it only when the
  binary or the definition changed. On Linux a drop-in
  (`spoor.service.d/10-outbox-group.conf`, `Group=spoor`) runs the service
  with the outbox readers' group: the unit's `StateDirectory=` makes
  systemd re-own `/var/lib/spoor`, recursively, to the service's user and
  group at every start, which is `root:root` without it. The state database
  is `0600` and the spools `0700`, so the group can read only the `0640`
  outbox. Services installed from the deb or rpm do not have the drop-in
  until `packaging/systemd/spoor.service` sets `Group=spoor`;
- with the extension tier, refuse a host where orbit's own
  `extensions.load` is in use (see "Three tiers"), copy the binary to
  `spoor.ext` and register it in **osquery's default `extensions.load`**
  (`/etc/osquery/extensions.load`, `/var/osquery/extensions.load`,
  `C:\Program Files\osquery\extensions.load`), never orbit's, which orbit
  itself truncates and rewrites; other lines in the file are kept, also a
  last line without a newline;
- restart orbit (or plain osqueryd) **detached and 10 seconds later** when the
  extension registration changed, because the script runs under orbit and a
  synchronous restart would kill it before Fleet gets its result.

Running a script twice changes nothing the second time. The `atc` tier
installs without the extension (and unregisters it). `uninstall-spoor.*`
removes the service, binary and registration and keeps configuration and
data unless `SPOOR_PURGE=1`. `register-extension.*` is the post-install
script for the Premium packages. The Windows script creates the service with
`New-Service` and updates its command line through `Win32_Service.Change`,
not `sc.exe ... binPath=`: Fleet runs scripts with Windows PowerShell 5.1,
which does not escape the quotes embedded in that command line, so sc.exe
would receive `C:\Program` as the program. Every native call checks its
exit code. The shell scripts run in a Debian container in `test/e2e`
(`TestFleetInstallScripts`); the PowerShell scripts and the macOS branch
have not been run (no Windows or macOS host); a unit test models PowerShell
5.1's argument passing for every `sc.exe` and `icacls.exe` call.

## Reports

| report | logging | why |
|---|---|---|
| spoor - detections | `differential_ignore_removals`, every 15 min, to the log destination | rows appear once; rows evicted by the table cap are not news |
| spoor - AI inventory (packed) | snapshot, every 4 h | one row per host; every list capped at 100 entries and each field clipped, with the true totals alongside, so the result stays under Fleet's 512 KiB per-host limit (tested with maximum-length values) |
| spoor - telemetry coverage | snapshot, hourly | not collected must never read as clean |
| spoor - sensor health | snapshot, hourly | version, profile, rule and bundle versions, counters |

Fleet keeps only the latest result per host and caps stored results, so it
is a state plane, not an event store: the event path for spoor is its NDJSON
outbox shipped by Fluent Bit (deploy/fluent-bit).

### Opt-in: exec events

`lib/opt-in/exec-events.reports.yml` joins osquery's evented process tables
(`process_events` on Linux, `es_process_events` on macOS,
`process_etw_events` on Windows) to `spoor_agent_processes`, reporting the
children and grandchildren of agent root processes. **Privacy warning:** a
Fleet-scheduled query over evented process tables sends raw command lines,
working directories and users to the Fleet server and its log destination,
outside spoor's privacy profiles, redaction and exclusions; command lines
routinely carry tokens. That is why spoor's daemon reads the same tables
locally over the osquery extension socket instead, and why these reports are
an example you must opt into, with `discard_data: true`. They also need
osquery's event flags (listed in each description).

A scheduled query over an evented table sees only the events since its
previous run, so the shell an agent started (depth 1) is usually in an
earlier batch than the command it runs (depth 2). The reports therefore also
look the parent up in osquery's `processes` table (accepted only if it
started no later than the child). A grandchild whose parent started before
the previous run and has exited is still not attributed; join earlier
depth-1 rows on `pid` at the destination to recover it.

## Verification

`verify.sh` checks this content against a live Fleet server with one
enrolled osquery host: GitOps dry run, ATC applied (and the original agent
options restored), every `spoor_*` table queried live, every policy shown to
pass on a healthy database and fail with a planted finding, a 25-hour-old
heartbeat and the database removed, Fleet's own policy results and label
membership after a refetch, and the same with the spoor extension instead of
ATC. Objects are applied one by one under a unique prefix and deleted
afterwards; it never runs `fleetctl gitops` without `--dry-run`. The state
database comes from the harness in `test/e2e/fleet_test.go` unless
`SPOOR_BIN` points at a spoor binary. A poll the host does not answer counts
as an error result and is retried, not a reason to stop the run. See
[VERIFIED.md](VERIFIED.md).
